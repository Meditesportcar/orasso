# Journal des choix

Ce que les documents de conception ne tranchent pas et que Claude Code a choisi (la solution la plus simple et cohérente avec les docs), pour relecture par Damien. Les entrées s'ajoutent à la fin de chaque section ; on ne réécrit pas une entrée, on la corrige par une nouvelle.

## Choix

### 15/10/2026 — Socle (lot 01)

- **Stack validée au démarrage, versions retenues.** Node 24.12 ; pnpm 12 ; TypeScript 6.0 ; Hono 4.13 sur `@hono/node-server` 2 ; React Router 8.4 (mode framework, rendu serveur) avec Vite 8 ; Expo SDK 57 (React Native 0.86, Expo Router 57) ; React 19.2.3 ; PostgreSQL 17 ; Drizzle ORM 0.45 et drizzle-kit 0.31 ; Better Auth 1.7 ; pg-boss 12 ; zod 4 ; Vitest 5 ; Biome 2.5. Aucun écart avec la stack de `CLAUDE.md`. Raison : versions courantes et compatibles entre elles (peer dependencies vérifiées). Fichiers : `package.json` de chaque paquet.
- **TypeScript 6.0 et non 7.0.** TypeScript 7 (réécriture native) est sorti, mais le modèle d'Expo SDK 57 est sur 6.0 ; une seule version pour tout le dépôt évite les surprises. À reconsidérer quand Expo passera à 7.
- **React 19.2.3 aussi sur le site.** C'est la version fixée par Expo SDK 57 ; avec `node_modules` à plat, une seule copie de React pour le site et l'appli évite les erreurs de « hooks » en double.
- **pnpm avec `nodeLinker: hoisted`, sans Turborepo.** Metro (Expo) gère mal les liens symboliques de pnpm ; les scripts racine utilisent `pnpm -r` / `pnpm --filter`. Seuls `esbuild` et les binaires PostgreSQL locaux sont autorisés à lancer un script d'installation (`allowBuilds`). pnpm a ajouté lui-même `minimumReleaseAgeExclude` pour des paquets publiés depuis moins longtemps que son délai de sécurité. Fichier : `pnpm-workspace.yaml`.
- **pnpm via corepack, installé dans le dossier utilisateur.** `corepack enable` échoue sans droits administrateur (il écrit dans `C:\Program Files\nodejs`) ; `corepack enable --install-directory "%APPDATA%\npm" pnpm` fonctionne et ce dossier est déjà dans le PATH. Fichier : `AVANCEMENT.md`.
- **Base locale : binaires PostgreSQL 17 du paquet `embedded-postgres`, pilotés par `pg_ctl`.** `pnpm db:start` initialise le dossier au premier lancement, démarre PostgreSQL en arrière-plan et crée la base ; `pnpm db:stop` l'arrête. Port, utilisateur, mot de passe et base viennent de `DATABASE_URL`, le dossier de `DB_DATA_DIR` : un worktree = un port et un dossier. Fichier : `scripts/db.mjs`.
- **Locale de la base : `builtin` `C.UTF-8`** (PostgreSQL 17), identique sous Windows et Linux, sans dépendre des locales du système. Le déploiement (lot 08) initialise sa base avec les mêmes options. Un tri « à la française » se fera par une collation ICU sur les colonnes qui en ont besoin.
- **Un seul pilote PostgreSQL : `pg` (node-postgres)**, partagé par Drizzle, Better Auth et pg-boss (qui l'utilise déjà).
- **Migrations.** `pnpm db:generate` (drizzle-kit) écrit les migrations versionnées dans `apps/api/drizzle/` ; `pnpm db:migrate` les applique avec le migrateur de drizzle-orm, sans drizzle-kit, donc utilisable tel quel sur le serveur. Le schéma `pgboss` est créé et mis à jour par pg-boss lui-même, hors migrations Drizzle. Fichiers : `apps/api/src/db/migrate.ts`, `apps/api/drizzle.config.ts`.
- **Tables de Better Auth au singulier** (`user`, `session`, `account`, `verification`, `two_factor`), colonnes en snake_case, plugin de double authentification activé dès le socle ; l'obligation pour les organisateurs et l'administration sera appliquée par l'API métier. Raison : conception technique du lot 02 (`ARCHITECTURE.md` § 1.1). Les clés d'accès (passkeys) viendront avec les comptes (lot 05). Fichiers : `apps/api/src/db/schema/auth.ts`, `apps/api/src/auth.ts`.
- **Pas encore de table `profiles`.** Pseudo, grade, points et le reste du profil sont décrits par `ARCHITECTURE.md` et arrivent avec le lot 05, pour ne pas poser deux fois le même modèle.
- **Connexion Google et Apple déclarées mais inactives** tant que leurs identifiants sont vides dans `.env`.
- **WebSocket** : support natif de `@hono/node-server` 2 avec `ws` (`@hono/node-ws` est déprécié). `/api/ws` renvoie pour l'instant ce qu'il reçoit.
- **Configuration** : un seul `.env` à la racine (API et scripts), validé par zod au démarrage de l'API ; l'appli lit `apps/mobile/.env` (`EXPO_PUBLIC_API_URL`), car Expo ne lit que le `.env` de son projet. Modèles : `.env.example`, `apps/mobile/.env.example`.
- **Ports de développement** : API 3001, site 5173 (Vite proxifie `/api` et `/api/ws` vers l'API : même origine, comme sur dev.orasso.fr), base 54329, Metro 8081.
- **API lancée par `tsx`**, sans étape de compilation, en développement comme en `start`. Le lot 08 décidera de la forme de l'image Docker.
- **Polices du site** : Archivo depuis Google Fonts (axes largeur 62–125, graisse 100–900, italique) et Archivo Narrow 700, présente dans la pile `narrow` de `tokens.json` et dans les aperçus des composants.
- **Icône et écran de démarrage de l'appli** : icône = `identite/favicon/icon-maskable-512.png` (fond Asphalte, marge de sécurité pour l'icône adaptative Android) ; écran de démarrage = monogramme fond sombre sur `#17191C`. Identifiants `fr.orasso.app` (Android et iOS).
- **Rôles partagés** : « organisateur » n'est pas un rôle de plateforme mais découle de l'appartenance à une structure (propriétaire ou co-organisateur) ; rôles de plateforme `user`, `moderator`, `super_admin`. Statut « désisté » d'une candidature : libellé « Désistée » (accordé avec « candidature », comme « Retenue »). Fichiers : `packages/shared/src/`.
- **Lint et format : Biome seul.** `docs/`, `identite/` et les copies de fichiers de marque (`apps/web/public`, `apps/mobile/assets`) sont exclus. Fichier : `biome.json`.
- **Fichier « Contexte orasso ( projet discussion claude ).txt » hors Git** (ignoré) : notes personnelles de Damien, déjà reprises dans `docs/00-contexte-projet.md`. Il reste sur le PC.
- **Vidéos lourdes de l'identité hors Git** (`identite/anime/*.mp4|*.mov|*.webm`) : elles restent sur le PC ; les GIF et SVG animés sont versionnés.

### 15/10/2026 — Architecture technique (lot 02, reportée par le lot 05)

Points que les docs ne tranchent pas, choisis par la conception technique (`ARCHITECTURE.md` § 8, à la racine du dépôt). Numérotation d'origine conservée.

- **C1 — Statut d'une offre de place non acceptée à temps.** Choix : statut terminal `expired` (pas de retour en fin de liste). Raison : prévisible, cohérent avec « ceux qui candidatent tard sont désavantagés » ; l'organisateur peut toujours re-retenir à la main.
- **C2 — Délai raccourci « 2 à 3 h ».** Choix : 3 h la veille, 2 h le jour J, plafonné au verrouillage, pas d'offre si < 30 min restantes, horloge décalée à 08:00 en heures calmes hors jour J. Raison : règle unique et testable ; évite des offres que personne ne peut voir.
- **C3 — Désistement après verrouillage.** Choix : autorisé jusqu'à la fin, marqué `withdrawn_after_lock`, malus à J+2, pas de réoffre. Raison : lecture littérale de « sans malus jusqu'au verrouillage » ; l'organisateur garde l'information ; la contestation permet de lever le malus.
- **C4 — Liste d'attente sur un événement sans limite de places.** Choix : aucune offre automatique ; liste manuelle. Raison : sans `capacity`, il n'y a pas de « place libérée ».
- **C5 — Nombre de véhicules par personne par défaut.** Choix : 1, réglable par événement. Raison : équité des places ; l'organisateur l'augmente s'il veut.
- **C6 — Statut Maintenu / Incertain / Annulé.** Choix : `outlook` (`maintained`/`uncertain`) distinct de `status` (`cancelled`). Raison : « Annulé » est irréversible et vide les candidatures ; « Incertain » ne change rien.
- **C7 — Recherche par plaque par le staff alors que « la plaque n'est visible que par l'organisateur ».** Choix : la liste synchronisée porte un hachage de la plaque normalisée et ses 3 premiers caractères, jamais la plaque entière. Raison : la recherche et le pointage par préfixe du prototype marchent hors ligne ; la plaque complète ne quitte pas le serveur (voir A10).
- **C8 — QR valide mais absent de la liste locale (inscription express d'un collègue).** Choix : résultat `unknown_pass` avec bouton « Accepter quand même » tracé. Raison : ne bloque pas l'entrée, reste visible au rapport.
- **C9 — Résolution des doublons entre appareils.** Choix : premier `scanned_at` gagne ; réécriture si un scan plus ancien arrive ensuite. Raison : un véhicule entre une fois ; l'heure d'entrée réelle est conservée.
- **C10 — Saison.** Choix : année civile. Raison : simple ; la plupart des événements sont de mars à octobre.
- **C11 — Barème et seuils.** Choix : +20 participation, +20 staff, +10 parrainage, −10 malus ; 0/100/300/400/800. Raison : chiffres du prototype validé (feuille « Points et grade ») ; les planches hésitent entre 400 et 500 pour Circuit : 400 retenu (prototype) ; constante partagée.
- **C12 — Fenêtre de contestation (« quelques jours »).** Choix : 7 jours après l'écriture du malus (J+2 → J+9). Raison : assez long pour les vacances, assez court pour clore.
- **C13 — Points staff « vérifiables ».** Choix : présence déclarée `present` au moment de J+2, modifiable par l'organisateur jusque-là. Raison : pas d'autre preuve disponible en V1.
- **C14 — Fenêtre du mode staff.** Choix : J−1 00:00 → `ends_at` + 1 jour ; mode jour J participant idem. Raison : « à partir de la veille », « fermé à J+1 ».
- **C15 — Heures calmes.** Choix : 22:00–08:00 Paris, levées le jour J et pour les alertes staff. Raison : « pas de notification la nuit, sauf le jour J ».
- **C16 — Motifs de refus.** Choix : constante partagée de 9 codes. Raison : la liste administrable viendra avec l'admin (lot 13).
- **C17 — Catégories.** Choix : une seule table pour véhicules, événements et centres d'intérêt, avec âge minimal. Raison : une liste à maintenir, et les affinités se calculent par simple intersection.
- **C18 — Motorisation.** Choix : texte court en V1 ; référentiel de motorisations plus tard. Raison : la « base construite par Orasso » n'existe pas encore.
- **C19 — Zones.** Choix : attribuées à la main par l'organisateur (tri) ou le staff placement ; pas de règle automatique. Raison : docs : « le staff placement voit qui va où ».
- **C20 — Format du QR d'inscription.** Choix : `OR1` + base64url (22 octets signés + 64 de signature), version 6. Raison : compact, préfixe de rejet rapide, pas d'URL pour rester petit.
- **C21 — QR de compte.** Choix : HOTP 60 s, 8 chiffres, identifiant court dérivé, fenêtre ±1, anti-rejeu 3 min. Raison : « comme une appli de double authentification » ; vérification côté serveur par le pro.
- **C22 — Horodatage des scans.** Choix : horloge de l'appareil, corrigée si > 24 h d'écart avec la réception. Raison : les files hors ligne peuvent attendre des heures.
- **C23 — Dates de « pointage en attente ».** Choix : entre `ends_at` et `settled_at`. Raison : J+2 vient des docs, l'affichage découle de `settled_at`.
- **C24 — Géographie.** Choix : lat/lng + boîte englobante, sans PostGIS. Raison : suffisant pour « autour de moi » par département/rayon.
- **C25 — Lignes `event_staff`.** Choix : créées à la publication pour tout le staff actif, puis à chaque nouveau staff. Raison : nécessaire pour les relances « je suis là ».
- **C26 — Suppression d'un véhicule.** Choix : réelle s'il n'a jamais candidaté, sinon archivage obligatoire. Raison : historique des événements conservé.
- **C27 — Champs « Accompagnants » et « Message » du formulaire (prototype).** Choix : colonnes `companions`, `message` (≤ 120). Raison : ce ne sont pas des questions personnalisées de l'organisateur ; utiles au tri.
- **C28 — Contestation sans réponse de l'organisateur.** Choix : escalade à l'administration après 7 jours. Raison : texte du prototype ; évite un malus qui reste en suspens.
- **Note sur C20** : le format du QR d'inscription a été corrigé par le coordinateur le 15/10 : `OR1` + base32 majuscules sans padding (mode alphanumérique, version 6-M), et non base64url (voir `ARCHITECTURE.md` § 3.1).

### 15/10/2026 — API A : comptes, garage, structures, événements, candidatures (lot 05)

- **Admission « sans sélection ».** Choix : la candidature est retenue d'office par le système (journal : acteur `system`, raison `admission.open`), ou mise en liste d'attente si l'événement est complet ; la liste d'attente est ensuite servie automatiquement. Raison : docs/01 (Validé) dit « tout le monde est accepté » ; l'architecture ne l'écrivait pas. Fichiers : `packages/shared/src/rules/applicationTransitions.ts`, `apps/api/src/modules/applications/service.ts` (`admitOpen`).
- **Place réservée par une offre.** Choix : une offre en cours réserve sa place. Retenir à la main exige `retenus + offres < capacité` ; accepter une offre exige seulement `retenus < capacité`. Raison : sinon l'organisateur pourrait prendre la place proposée à quelqu'un qui a encore le droit de l'accepter. Fichier : `applications/service.ts`.
- **Rang affiché en liste d'attente.** Choix : position parmi les candidatures en liste d'attente (1 = prochain servi), recalculée à la lecture ; `waitlist_rank` ne sert qu'à l'ordre. Une offre retire le rang. Le compteur « liste d'attente » du tri inclut les offres en cours (même libellé « Liste d'attente » côté candidat). Fichiers : `applications/queries.ts`, `events/repo.ts`.
- **Pseudo à l'inscription.** Choix : le champ `name` de l'inscription Better Auth porte le pseudo demandé ; le profil est créé par un crochet d'inscription ; si le pseudo est pris ou invalide, un pseudo suffixé de chiffres est attribué (modifiable). Pseudos : 3–24 caractères, lettres (majuscules permises, comme « Damien_66 »), chiffres, « _ », « . », uniques sans tenir compte de la casse. Fichiers : `apps/api/src/auth.ts`, `modules/profiles/service.ts`.
- **Référentiel véhicules de départ : source et méthode.** Rédigé à partir des connaissances générales sur les véhicules courants des rassemblements (JDM, allemandes, françaises, italiennes, américaines, anglaises, suédoises, coréennes ; quelques motos et utilitaires), années de production européennes les plus communément admises, puis contrôlé par script (doublons, années). Volume : 47 marques + « Autre », 240 modèles + un « Autre » par marque, 669 générations + un « Autre » par modèle. Le modèle « Autre » accepte tous les types de véhicule. À relire par l'équipe Orasso : découpages Kawasaki Z1000, Yamaha R1 / R6 / MT-09 (générations nommées par année ou « Gen N »), chevauchement Jaguar XJ, fin du Volkswagen Combi T6 fixée à 2024. Fichier : `apps/api/src/db/seed/vehicle-reference.ts`.
- **Numérotation des migrations.** Choix : `0001_profiles` à `0007_admin` (l'architecture annonçait `0002` à `0008`, mais le socle n'avait que `0000_auth`). La contrainte d'unicité `(vehicle_id, position)` des photos est rendue `DEFERRABLE INITIALLY DEFERRED` à la main dans `0003_vehicles.sql` (réordonnancement en une transaction).
- **Notifications : colonne `delivered_at`.** Choix : ajoutée à `notifications` pour réserver chaque livraison une seule fois (idempotence). Livraison tout de suite après la décision (et par la tâche `notifications.deliver` chaque minute pour les notifications différées) ; e-mail quand aucun appareil push n'est actif (plus les types « toujours par e-mail ») ; famille coupée dans les préférences → la notification reste dans le Journal, sans push ni e-mail. Une notification différée (heures calmes) n'apparaît dans le Journal qu'une fois livrée. Fichier : `modules/notifications/service.ts`.
- **Routes publiques par slug.** Choix : `GET /api/events/by-slug/:slug` et `GET /api/structures/by-slug/:slug` ; `GET /api/events/:id` et `/api/structures/:id` restent les vues organisateur. Raison : l'architecture mettait le slug et l'identifiant sur le même chemin.
- **Membres d'une structure.** Choix : invitation d'un compte existant (pseudo ou e-mail) au statut `invited`, acceptée ou déclinée par l'intéressé (`POST /api/me/memberships/:structureId/accept|decline`) ; le propriétaire gère les co-organisateurs, propriétaire et co-organisateurs gèrent le staff ; le propriétaire ne se retire pas (pas de transfert de propriété, docs/01). L'invitation d'une adresse sans compte et la demande venant de l'utilisateur : lot 13.
- **Événement sur invitation.** Choix : candidature refusée (`403`) tant que les invitations nominatives (lot 13) n'existent pas ; page visible seulement des membres de la structure et des candidats.
- **Tâches pg-boss sans « singleton ».** Choix : chaque tâche d'événement porte l'instant prévu (`at`) ; à l'exécution, si l'instant recalculé depuis la base diffère (date modifiée), la tâche ne fait rien et la nouvelle tâche planifiée prend le relais. Rappel de la veille à 18:00 (Paris). Fichiers : `modules/events/jobs.ts`, `src/jobs.ts`.
- **Staff de filtration.** Choix : il voit la liste de tri sans plaque ni coordonnées, donne son avis, et ne décide que si l'organisateur lui a donné `can_decide` (journal : acteur `staff`). Les rôles viennent de la structure ; l'ajustement par événement arrivera avec `event_staff` (lot 06).
- **Historique du candidat au tri.** Choix : « nombre d'événements » = candidatures retenues sur des événements terminés ; « absences » = 0 jusqu'au pointage (lot 06).
- **Motifs de refus.** Choix : les 7 codes listés par l'architecture (le point C16 annonçait 9 codes, la liste en compte 7).
- **Échéance d'offre la nuit à J−3.** L'exemple de test de l'architecture (§ 2.2, « offre à 23:00 J−3 → échéance J−2 08:00 ») contredit la règle écrite juste au-dessus (départ 08:00 J−2, délai 24 h → J−1 08:00). C'est la règle qui est codée et testée.
- **Photos.** Choix : recompression en WebP 80, 2048 px au plus, orientation EXIF appliquée, métadonnées retirées ; avatar carré 512 px. Le HEIC est refusé quand libvips (sharp précompilé) ne sait pas le lire : l'appli convertira en JPEG avant l'envoi. Fichier : `modules/vehicles/service.ts`.
- **Validation.** Choix : un petit utilitaire `lib/validate.ts` (zod 4 direct) au lieu de `@hono/zod-validator` ; les sorties sont typées en TypeScript dans `packages/shared/src/schemas/` (pas de validation à l'exécution). Requêtes réutilisées dans `repo.ts`, requêtes ponctuelles dans le service (écart assumé à « aucune requête hors repo »).
- **Tests de l'API.** Choix : base dédiée `<base>_test` sur le même serveur local, créée et migrée automatiquement au lancement (`apps/api/test/global-setup.ts`) ; tables vidées avant chaque test (les services ouvrent leurs propres transactions, l'annulation par test n'est pas possible). La base de dev et son seed ne sont jamais touchés. Le scénario du critère de fin est un test d'intégration (`apps/api/test/scenario-parcours1-a.test.ts`), pas un script.
- **Seed de démonstration.** Choix : 120 comptes générés (26 en `--small`) au lieu de 12, pour atteindre les volumes du prototype (166 candidatures sur la Nocturne, 2 véhicules au plus par personne) ; co-organisatrice « Sarah_66 » ; un seul mot de passe pour les comptes de démonstration (`SEED_PASSWORD` du `.env`) ; points de Damien (340, Sport) et de Kenji (120, Route) écrits directement dans le cache du profil (les écritures de points arrivent au lot 06) ; Damien n'a pas de 2FA dans le seed, d'où `DEV_SKIP_2FA=true` en développement. Photos factices générées (dégradé + silhouette). Fichier : `apps/api/scripts/seed.ts`.
- **Slug d'un événement.** Choix : titre + année (`nocturne-de-canet-2026`), suffixe aléatoire s'il est pris.
- **Corrections après relecture (lot 05).** (1) Les schémas de mise à jour (`PATCH` événement, structure, zone) n'ont plus de valeurs par défaut : avec zod 4, `.partial()` les gardait et un changement de titre remettait la capacité à « sans limite » ; les défauts ne vivent que dans les schémas de création. (2) Échéance d'une offre : pas d'offre s'il reste moins de 30 min entre l'**envoi** de l'offre (après les heures calmes) et l'échéance, et non entre la décision et l'échéance (sinon, la veille au soir d'un événement matinal, l'offre expirait avant d'être notifiée) ; `ARCHITECTURE.md` § 2.2 mis à jour. (3) Verrous toujours pris dans le même ordre, événement puis candidature (pas d'interblocage entre candidat, organisateur et tâches). (4) Tâche d'expiration partie en avance : replanifiée ; balayage `waitlist.sweep` chaque minute pour une offre échue dont la tâche n'est pas passée. (5) Livraison des notifications lancée sans faire attendre la requête, lignes réservées avec `FOR UPDATE SKIP LOCKED`, réessayée à la minute suivante en cas d'erreur. (6) `db:seed --reset` refusé en production (sauf `--force-production`), `SEED_PASSWORD` obligatoire en production. (7) Recherche du tri et des événements : `%` et `_` échappés. (8) Avant-première non annoncée pour un événement sur invitation.
- **Déploiement sur dev.orasso.fr (consignes du lot 08).** Photos dans `UPLOADS_DIR` (`/data/uploads` sur le VPS) ; la route d'envoi est `POST /api/me/vehicles/:id/photos` (la `location` nginx à 128 Mo existe déjà) ; l'avatar (`POST /api/me/avatar`, 16 Mo au plus) passe sous la limite générale. E-mails « journal » : console et table `email_outbox` seulement quand le dossier n'est pas inscriptible (conteneur). Variables nouvelles ajoutées à `deploy/dev.env.example` : `SEED_PASSWORD` (à générer sur le VPS), `MAIL_TRANSPORT`, `MAIL_FROM`, `BREVO_API_KEY`, `EXPO_ACCESS_TOKEN` ; `DEV_SKIP_2FA` ne doit jamais y figurer.
### 15/10/2026 — Design system web (lot 03)

Fichiers : `packages/design-system/` (jetons, composants), `apps/web/app/routes/ds.tsx` (page `/_ds`), `apps/web/app/root.tsx`.

- **Largeur étroite : Archivo sur l'axe `wdth`, plus Archivo Narrow.** `tokens.json` met « Archivo Narrow » en tête de la pile `narrow`, alors que le README dit « Archivo seule, en trois largeurs ». Mesure dans le navigateur (texte « Prochain accès · J-2 Sam 17 oct JDM », graisse 700) : Archivo Narrow = 597,5 px, Archivo à `wdth` 78 % = 594,1 px, 80 % = 604,5 px, donc 78,4 % donne la même largeur, et le rendu superposé est indiscernable. Le site utilise donc `--stretch-narrow: 78.4%` et `--font-narrow: "Archivo", system-ui, sans-serif` (surcharge dans `base.css`). `tokens.ts` garde la valeur du JSON telle quelle : le lot 04 (natif) tranchera pour React Native, où la largeur d'une police variable ne se règle pas de la même façon. Le site ne charge plus Archivo Narrow ni Google Fonts.
- **Polices auto-hébergées** (SSR et hors ligne) : Archivo variable (axes `wdth` 62–125 et `wght` 100–900), droit et italique, sous-ensembles latin et latin étendu (4 fichiers woff2, environ 370 Ko, licence OFL) dans `packages/design-system/src/web/fonts/`. Le vietnamien n'est pas inclus (inutile pour un site français).
- **Thème : préférence `beton` | `sable` | `auto`, Béton par défaut.** `auto` suit le mode clair de l'appareil (Sable) ou sombre (Béton). La préférence est un cookie `orasso-theme` (un an) doublé d'un `localStorage` : le serveur lit le cookie et écrit `data-theme` dans le HTML (aucun flash) ; pour `auto`, un script bloquant en `<head>` pose l'attribut avant la première peinture. Le thème est l'attribut `data-theme` de `<html>` ; `ThemeScope` l'applique à une zone (démo des deux thèmes côte à côte, aperçu d'une structure). Le basculement automatique selon le lever du soleil (staff, appli) relève de l'appli.
- **Jetons générés, sorties versionnées.** `scripts/generate-tokens.mjs` lit `docs/design-system/tokens.json` et écrit `src/tokens.ts`, `src/web/tokens.css` et `src/web/typography.css` ; il tourne dans `build` et avant `test`. ### 15/10/2026 — Design system natif (lot 04)

Fichiers : `packages/design-system/src/native/` (entrée `@orasso/design-system/native`), `scripts/generate-native-*.{mjs,py}`, `apps/mobile/src/ds/Demo.tsx` (route cachée `/_ds`), `apps/mobile/src/app/_layout.tsx`.

- **Largeur étroite en natif : six instances statiques d'Archivo, pas d'axe variable.** Sur Android l'axe `wdth` d'une police variable n'est pas pris en charge. `scripts/generate-native-fonts.py` (fontTools) fige les polices variables du site en TTF : Expanded 125 % Noir droit et italique, étroite 78,4 % Gras (même largeur que sur le site, voir lot 03), 100 % Regular, SemiBold et ExtraBold (~41 Ko chacune, latin). Pas d'Archivo Narrow. En natif on n'écrit pas `fontWeight` : le nom de la famille (`Archivo-Narrow-Bold`…) porte largeur, graisse et style (`fontFamily.ts`). Le script n'est relancé que si les polices du site changent ; les TTF sont versionnés.
- **Mêmes noms, mêmes props que le web, quand React Native le permet.** Écarts : `onPress` au lieu de `onClick`/`href` ; `Photo` est une image `{source}` ou un dégradé de maquette `{placeholder}` (pas un nœud React) car React Native n'a pas de `clip-path` : la coupe à 10° est un polygone SVG ; `title` de PosterCard est une chaîne (`\n` pour le saut de ligne) ; `CheckboxField` est contrôlé (`checked`/`onChange(bool)`) ; `SelectField` ouvre une liste en plein écran (`Modal`) au lieu d'un `<select>`. Ajoutés au natif : `Sheet` (feuille), `OpeningScreen`/`OpeningLogo`, `Text` (styles de texte), `Photo`.
- **Thème par contexte** : `ThemeProvider` (Béton par défaut ; `auto` = mode clair de l'appareil → Sable, sombre → Béton) ; la préférence n'est pas écrite sur le disque par le paquet (`initialPreference` / `onPreferenceChange` : l'appli la mémorise, lot 09) pour ne pas imposer de dépendance de stockage. `ThemeScope` applique un thème à une zone. Réduction des animations : `AccessibilityInfo` (suivi en direct), forçable par `reducedMotion` (recette : `/_ds?reduce=1`).
- **Les ombres des jetons passent telles quelles** (`boxShadow` en chaîne CSS, y compris `inset` et plusieurs couches : React Native 0.86 les prend en charge). Les fusions (`overlay`, `multiply`, `screen`) passent par `mixBlendMode`, la transformation d'origine par `transformOrigin`. Non vérifié sur appareil (voir « À revoir »).
- **Fonds et barres redessinés avec `react-native-svg`, pas `expo-linear-gradient`** (la dépendance n'apporte rien de plus : les dégradés radiaux elliptiques et les bandes du marquage sont en SVG). Les dégradés CSS des jetons (`groundFx`, `barFx`) sont lus au démarrage par `gradientCss.ts` (radial elliptique, linéaire à angle, répété à bandes franches ; « transparent » prend la teinte du voisin comme en CSS) puis dessinés pour la taille mesurée. Le DOM SVG ignore `rx`/`ry` sur `radialGradient` (le web n'aurait vu qu'un cercle) : l'ellipse est un cercle de rayon `rx` écrasé par `gradientTransform`.
- **Grain et brossage : bruit recalculé, pas feTurbulence.** `react-native-svg` 15 déclare `FeTurbulence` mais ne le rend pas (avertissement « non implémenté »). `noise.ts` recalcule la fonction de référence de la spécification SVG (bruit fractal, mêmes fréquences, octaves, couleur et alpha que les jetons `grain` et `barBrush`, tuile qui se raccorde grâce à `stitchTiles`) une seule fois, en une tuile PNG indexée (couleur constante + alpha par pixel, 256×256 pour le grain, 512×64 pour le brossage, ~65 et ~33 Ko en mémoire), répétée en `resizeMode="repeat"` avec l'opacité et la fusion des jetons.
- **Marque.** La géométrie du logotype, du monogramme, du chargement et du logo animé d'ouverture est extraite des SVG du kit (`scripts/generate-native-brand.mjs` → `brandArt.ts`, versionné, lancé par `generate` et `pretest`) ; les couleurs d'encre du kit (crème, noir, moutarde de la voiture) sont celles des fichiers de marque, pas des jetons de thème. Chargement : la voiture se déplace en animant `x` des rectangles et `d` du masque des vitres (animer `transform` sur `G` ne passe pas par la couche native de react-native-svg) ; ses images clés et courbes sont celles du SVG d'origine. Ouverture : logo animé 1,6 s (voiture, O qui prend sa place, lettres découvertes par un rideau de largeur animée) ; « reduce motion » : logo garé.
- **Mouvement.** `park` = deux segments (60 % `park` jusqu'à −6 px, 40 % `inout`) sur `base`, comme le web. Un seul néon pulse à la fois (`neon.ts` : le pic du résultat de scan OK et le tampon du bandeau d'une affiche demandent le droit de pulser ; si un autre pulse, ils s'allument sans pic). Le pic de néon du scan ne joue que pour **OK** (le web le joue aussi sur « déjà entré » : le README dit « un néon ne pulse que pour un événement »). La coupe à 10° de `Reveal` est un rideau diagonal (largeur animée d'un cadre incliné, contenu redressé), retiré à la fin pour ne pas rogner l'ombre. Le fondu croisé d'écran (`ScreenTransition`) garde l'ancien écran 160 ms.
- **Feuille (`Sheet`)** : voile à 80 % (`night`), se gare du bas (ou du haut pour le Journal) avec 6 px de dépassement ou part du point `origin` donné (centre de la cloche, de l'avatar) ; posée en dernier enfant d'un conteneur plein écran, sans `Modal`.
- **Résultat de scan** : la carte au bas de la caméra (comme le web) et un mode `fullscreen` (couleur pleine, grande icône, nom en 26 px, zone en 72 px, retour automatique `onReturn` après `scan` = 1 s) pour « résultat plein écran coloré » de `docs/02`. Tailles du plein écran : choix (non écrites dans les docs). Trois sons **provisoires** générés par `scripts/generate-scan-sounds.mjs` (synthèse pure, aucune source externe, aucun droit) : OK = deux notes montantes brèves (~280 ms), déjà entré = deux bips identiques (~250 ms), refusé = son grave rugueux (~420 ms). Lecture avec `expo-audio` (`playScanSound`, qui ne lève jamais). À remplacer par un vrai design sonore : il suffit de remplacer les trois fichiers de `sounds/`.
- **Barre d'onglets : 16 px réservés au-dessus** (`TAB_OVERHANG`) : l'onglet central déborde vers le haut, et sur Android un enfant hors des limites de son parent ne reçoit pas les appuis ; la barre mesure donc 96 px (+ zone de sécurité), le haut transparent. `AppBar` et `TabBar` prennent la zone de sécurité (`safeTop`, `safeBottom`) en propriété : l'appli passe `useSafeAreaInsets()`.
- **Pas de flou d'arrière-plan** sur les pastilles flottantes (`FloatingMark`) : il faudrait `expo-blur`, une dépendance de plus pour un détail ; voile `night` à 55 % seul.
- **Dépendances ajoutées à `apps/mobile`** (versions de `expo install`) : `react-native-svg`, `react-native-reanimated` + `react-native-worklets` (exigée par Reanimated 4), `expo-font`, `expo-audio`, et pour la recette sur navigateur `react-native-web`, `react-dom`, `@expo/metro-runtime`. Rien d'autre (`expo-linear-gradient` et `expo-haptics` essayés puis retirés). Dans le paquet, tout est en `peerDependencies` optionnelles : le site n'en dépend pas.
- **Aperçus d'origine.** Comparaison visuelle faite avec la page `/_ds` du site (lot 03, déjà comparée aux `preview.html`) et les règles CSS des composants web, pas avec les `preview.html` eux-mêmes (le harnais du lot 03 s'appuie sur la pile du site ; il n'a pas rendu correctement hors d'elle).
